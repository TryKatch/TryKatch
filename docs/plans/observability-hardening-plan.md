# Observability hardening implementation plan

Status: proposed; implementation is not included in this document.  
Repository baseline: `develop`, inspected 2026-09-09.  
Applies to: the generated Trykatch application under `templates/trykatch` and the template's verification/documentation workflows.

## Outcome and scope

Qualify the existing OpenTelemetry → Collector → Loki/Tempo/Prometheus → Grafana path for staging and a modest, single-host production deployment. Preserve local Aspire development, structured console logging, application availability during telemetry outages, and the existing separately persisted audit records.

Concentrate application policy behind the ServiceDefaults interface; concentrate transport, storage, and operator policy in the existing deployment configuration. Keep Serilog as the sole `ILogger` provider and OTLP log exporter. Do not add a second SDK log pipeline or collect stdout into Loki in parallel with Serilog OTLP.

This plan does not introduce Kubernetes, cloud-specific resources, a service mesh, Kafka, a Collector agent/gateway fleet, multi-host high availability, production Aspire Dashboard hosting, browser telemetry, a new logging abstraction, or a replacement deployment system. Migrator instrumentation and host-wide monitoring are separate work. Head sampling will not promise complete error traces. Persistent Collector queues will not promise exactly-once delivery or protection from host/disk loss.

The source material is [the repository's production guidance](../research/aspire-opentelemetry-production-guidance-2026-09-09.md), verified against current primary documentation again on 2026-09-09. Official behavior is cited below. Ratios, retention periods, thresholds, and qualification workloads are proposed Trykatch defaults, not Microsoft or OpenTelemetry requirements. Validate version-sensitive settings against the pinned binaries before merging: Aspire 13.5.3, OpenTelemetry .NET 1.18.0, Serilog OTLP sink 4.2.0, Collector contrib 0.160.0, and the existing backend image digests.

## Intended interface and ownership

Keep `builder.AddServiceDefaults()` as the registration seam. It owns a single resolved observability policy used by the SDK and Serilog adapters. Add `app.UseServiceDefaults()` as the small middleware entry point for safe request logging; retain `app.MapDefaultEndpoints()` for probes. `Program.cs` should know these calls and their normal registration/middleware/mapping order, not sampler classes, resource dictionaries, OTLP sink options, or sanitization rules.

Put implementation under `src/TrykatchApp.ServiceDefaults/Observability/`: an internal resolved-policy value, resource/transport resolution, SDK setup, and Serilog event projection/sink setup. Use framework-native configuration and options validation internally; do not expose separate public builders for every signal. Move the API's three Serilog package references to ServiceDefaults as needed, preserving central package management and lockfiles. This is a deep module: removing it would scatter resource precedence, protocol translation, redaction, request policy, and lifecycle behavior across callers.

Tests exercise the same registration and middleware seam with a test host and recording OTLP receiver. They must not depend on private helper names. Deployment YAML is the second real seam: the existing private single-host network and an opt-in authenticated TLS configuration are its concrete adapters. Application modules keep using `ILogger`, `ActivitySource`, and `Meter`; no module-specific exporter configuration is introduced.

## Phase 1 — Consistent identity and explicit export contract

Files: `ServiceDefaults/Extensions.cs`; new `ServiceDefaults/Observability/*.cs`; ServiceDefaults/API project files; API `Program.cs`; AppHost `Program.cs`; both Compose files; `.env.example`; relevant `packages.lock.json`; new `tests/TrykatchApp.IntegrationTests/ObservabilityContractTests.cs` and fixture.

1. Resolve one resource identity per host: `service.name`, `service.namespace`, `service.version`, `service.instance.id`, and `deployment.environment.name`. Use the configured `OTEL_SERVICE_NAME`, approved values from `OTEL_RESOURCE_ATTRIBUTES`, the deployment's environment/build metadata, and a process-lifetime instance fallback. Preserve an Aspire-provided instance identifier; otherwise generate one once and share it across SDK and Serilog. Two concurrently running hosts must have distinct instance IDs. Do not use an organization ID, hostname containing user information, or a deployment secret as identity. Follow the [OpenTelemetry service conventions](https://opentelemetry.io/docs/specs/semconv/resource/service/).
2. Document and test precedence: explicit standard OTEL identity values win over application defaults; `OTEL_SERVICE_NAME` wins over `service.name` in resource attributes. The environment name defaults from the .NET host environment using a documented mapping. Version comes from CI/build configuration with assembly informational version as a development fallback. Production Compose supplies an immutable release identifier; it must not silently use `unknown_service` or a development placeholder. Additional resource attributes are allowlisted by policy.
3. Use the generic OTLP endpoint/protocol/headers as the supported common export configuration. Explicitly choose `http/protobuf` in both Compose and AppHost. The resolver may support the standard `grpc` alternative, but test both mappings; never infer protocol from port number. Define how signal-specific OTEL overrides are handled: reject conflicting values with a sanitized startup validation error until independent destinations are deliberately supported. Test configuration from `IConfiguration`, not only process environment. Preserve development and existing integration-test startup without an endpoint as console-only/no-export mode. Validate only enabled export settings.
4. Apply the resolved endpoint, protocol, headers, and resource to both adapters explicitly. Disable the Serilog sink's independent environment override behavior after resolution to prevent a second precedence system. The [official Serilog sink documentation](https://github.com/serilog/serilog-sinks-opentelemetry) documents its environment overrides and `ignoreEnvironment`; the [OTLP configuration specification](https://opentelemetry.io/docs/languages/sdk-configuration/otlp-exporter/) distinguishes base endpoints from per-signal endpoints. Verify HTTP requests reach `/v1/logs`, `/v1/traces`, and `/v1/metrics` without repeated suffixes.
5. Make Compose endpoint/environment/version settings actually configurable and make `.env.example` match consumed variables. Keep the two template variants equivalent. Do not print exporter headers or full configuration in validation failures.

Acceptance: a single test request exports correlated logs and traces plus a request metric with identical five-field resource identity; two hosts differ only where expected; only one log copy arrives; AppHost and Compose both reach all three HTTP signal endpoints. Configuration conflicts fail clearly without exposing values. Existing OpenAPI generation and endpoint-free integration tests still work.

## Phase 2 — Sampling and health noise policy

Files: ServiceDefaults observability implementation and endpoint mapping; API `Program.cs`; both Compose files; `.env.example`; new observability contract tests; `web/apps/web/nginx.conf` only if explicit probe routing protection is needed.

1. Use parent-based sampling with a ratio root sampler. Set explicit defaults of 1.0 for local development and 0.10 for staging/production, adjustable through `OTEL_TRACES_SAMPLER` and `OTEL_TRACES_SAMPLER_ARG`. Reject malformed or out-of-range values. Honor sampled/unsampled parents and document that remote sampled parents can increase intake above the root ratio. Keep metrics and operational error logs unsampled. This follows [OpenTelemetry .NET sampling guidance](https://opentelemetry.io/docs/languages/dotnet/sampling/); 10% is an initial capacity hypothesis.
2. Describe error/slow-trace limits honestly: head sampling cannot recover discarded spans. Error metrics and sanitized error logs remain available; some log trace links will have no stored trace. Tail sampling is deferred until a measured requirement justifies its memory, delay, and complete-trace routing costs. Never connect audit retention or correctness to trace sampling.
3. Apply `.DisableHttpMetrics()` to mapped health endpoints, retain trace suppression, and suppress successful probe request logs before either Serilog sink. Include health and future scrape endpoint matching in one internal policy; test path-segment behavior so `/healthcare` is not accidentally suppressed. Preserve sanitized failed-probe diagnostics. Microsoft's [ASP.NET Core metrics documentation](https://learn.microsoft.com/en-us/aspnet/core/metrics/overview?view=aspnetcore-10.0#opt-out-of-http-metrics-on-certain-endpoints-and-requests) documents endpoint-level metric exclusion.
4. Account for readiness-check child Npgsql/HTTP telemetry; verify successful probes do not generate hidden database spans or log floods. Use supported instrumentation suppression around probe execution if needed. Define the achievable contract precisely: exclude route request histograms/traces/logs; aggregate runtime/process/database-pool metrics need not be attributable to, or excluded for, an individual probe.
5. Keep `/health/live` process-only and `/health/ready` dependent on PostgreSQL, not telemetry backends. Verify operational routes remain private behind the React proxy. Document ingress denial/private routing for backend-only deployments, where API port 8080 is directly published. Keep internal Docker health checks functional; do not add application-login requirements to container probes. See [Aspire health checks](https://aspire.dev/fundamentals/health-checks/).

Acceptance: deterministic trace-ID and parent-context tests verify sampling at 0, 0.1, and 1; 1,000 successful probes add no request logs, request-duration samples, or probe spans; a real application request still produces signals. A failed readiness check is observable, and Collector/backend failure does not change application readiness.

## Phase 3 — Source minimization and Collector privacy enforcement

Files: ServiceDefaults observability implementation; `Infrastructure/Persistence/OutboxDelivery.cs` and other confirmed unsafe log call sites; `deploy/observability/otel-collector.yml`; new privacy fixtures/tests; `docs/threat-model.md`.

1. Define the export schema before implementing processors. Approved fields include stable event IDs/templates, route templates, HTTP method/status, bounded outcome, exception type, selected database operation metadata, and trace/span correlation. Prohibit credentials, authorization/cookie headers, bodies, tokens/reset/invitation URLs, connection strings, raw SQL/parameters, raw query strings, emails, personal names, arbitrary baggage, organization/user identifiers, and uncontrolled object destructuring. Review current instrumentation outputs rather than assuming library defaults are safe. Limit string lengths, attribute counts, and event sizes.
2. Project/redact Serilog events before both console and OTLP sinks; sink-only Collector filtering cannot protect stdout. Replace raw request paths with route templates where possible and use a bounded unmatched-route value. Remove arbitrary exception messages and stack text that embeds messages; retain safe exception type, error/event code, and correlation. Use reviewed fixed message templates and approved structured values for built-in sensitive flows. Do not claim regex masking alone protects arbitrary log bodies. Additional application log templates/fields must follow the same documented review contract.
3. Change outbox telemetry to export a safe failure classification and exception type instead of the raw exception message/event. Keep delivery retries, message processing, and stored business state intact; this work does not alter database audit or outbox retention. Decide explicitly whether opaque message IDs are retained as non-indexed trace/log attributes; never make them metric or Loki index labels. Test failures from a transport whose exception contains a planted payload secret.
4. Add Collector per-signal attribute allowlisting and targeted redaction before batching and persistent exporter queues: `memory_limiter → privacy processors → batch → exporter`. Cover resources, log attributes/body, span attributes/events/status descriptions/names, and metric attributes. Preserve trace/span IDs and required semantic fields. Processor configuration is executable policy, validated against the pinned [transform processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.160.0/processor/transformprocessor) and [redaction processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.160.0/processor/redactionprocessor). Choose only the processors needed for the specified fields; do not build a general privacy engine.
5. Define privacy processing failure behavior explicitly: malformed supported inputs must be rejected/dropped, never forwarded unsanitized. For security-critical transformations use tested error propagation and type guards, and monitor rejected data. Keep Collector payload debug output disabled. Verify that processor error logs cannot echo planted content. OpenTelemetry's [sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/) places minimization responsibility on the implementer.
6. Apply metric tag selection before aggregation through SDK views. Do not simply delete distinguishing metric attributes after aggregation and silently merge conflicting time series; reject unexpected streams or use a tested aggregation path when needed.

Acceptance: synthetic credentials and PII planted in headers, query/path, nested properties, exception text, SQL attributes, baggage, and direct OTLP fixtures never appear in captured application stdout, Collector diagnostics, Loki or Tempo query results, or Grafana datasource responses. Positive controls prove sanitized records reached each destination, so an empty pipeline cannot pass. Safe IDs/templates, HTTP status, outbox outcomes, and trace/log correlation remain usable.

## Phase 4 — Deployment trust and TLS/authentication extension

Files: both Compose variants; AppHost `Program.cs`; `.env.example`; Collector config; new opt-in Collector TLS configuration under `deploy/observability`; ServiceDefaults transport policy; operations/threat-model documentation; TLS fixture tests.

1. Document the current trust model: one controlled Docker host, private Docker network, no published Collector/Loki/Tempo/Prometheus ports. Plaintext inside this explicitly defined trusted network remains supported. Restrict Grafana's default host binding to loopback and require non-default credentials; operators expose it through their authenticated HTTPS operational ingress. Ensure application containers cannot accidentally reach a publicly bound unauthenticated OTLP endpoint through template defaults.
2. Support HTTPS and secret-supplied exporter headers in the common application policy, with normal certificate validation for both SDK and Serilog. Provide a tested opt-in Collector receiver configuration for TLS plus bearer-token authentication, and documented custom-CA trust/mounting. Use secret files/providers for token material; never include real tokens/certificates in YAML, source, logs, or CI artifacts. Do not offer certificate-validation bypasses as a production option.
3. Show secure outgoing Collector OTLP exporter settings for a remote backend, including CA trust and authentication. An HTTPS URL alone does not secure the Collector-to-backend hop. Require authenticated TLS whenever a telemetry hop leaves the declared host/trust domain. Base this on [Collector configuration security guidance](https://opentelemetry.io/docs/security/config-best-practices/). More complex workload identity or mTLS may replace the deployment adapter later without changing application callers; they are not mandatory template infrastructure.
4. Keep the base configuration immediately usable without certificates. Validate base and TLS configuration independently with the same pinned Collector image. Remove the API's mandatory startup dependency on Collector and the Collector's unnecessary backend startup dependency; exporters retry asynchronously, and business startup remains governed by migrator/database readiness. Preserve deliberate database ordering.

Acceptance: base Compose still exports all signals; telemetry backend ports are inaccessible from host/public ingress unless explicitly enabled; HTTPS with a trusted CA and correct token exports all signals; absent/wrong token and untrusted certificates fail export without making API readiness fail. Starting the API while the Collector is absent succeeds once business dependencies are ready.

## Phase 5 — Bounded recovery and Collector self-monitoring

Files: Collector config; both Compose files; AppHost writable-volume configuration; Prometheus config; new recovery tests and operations runbook.

1. Configure explicit bounded sending queues and retry intervals for Loki and Tempo network exporters. Use `file_storage` on a dedicated writable named volume while keeping the container root filesystem read-only. Configure ownership and startup permissions without root/capability expansion. Pin and validate the [file storage extension](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.160.0/extension/storage/filestorage) and [exporter helper queue settings](https://github.com/open-telemetry/opentelemetry-collector/tree/v0.160.0/exporter/exporterhelper).
2. Start qualification at 20 requests/second with 10% root sampling and a five-minute backend outage; derive queue capacity from measured exported records/bytes per second × 300 seconds × 2 safety factor. Record the configured queue units, consumers, retry horizon, maximum batch size, disk usage, and 512 MiB Collector container budget. Measure actual log volume and sampled-parent scenarios rather than assuming one record per request. Adjust the proposed workload or limits transparently if the baseline host cannot sustain them.
3. Distinguish delivery guarantees: queues protect accepted/enqueued logs and traces across Collector restarts, with duplicates possible; SDK memory queues, unflushed Collector batches, exhausted retries, full disk, and host loss remain loss windows. The Prometheus pull exporter has no durable outbound sending queue: scrapes missed during Collector downtime are missing, and cumulative-counter recovery must be tested. Do not route it through a fictitious WAL. Follow [Collector resilience guidance](https://opentelemetry.io/docs/collector/resiliency/).
4. Give Collector a bounded graceful shutdown period and verify API SDK/Serilog disposal flushes within the existing 30-second application grace period. Bound exporter waits and memory during outages. Test graceful termination separately from a forced Collector restart so the residual loss window is visible.
5. Explicitly expose Collector internal Prometheus telemetry on the private network, conventionally port 8888, using the current `service.telemetry.metrics.readers` syntax. Add a separate Prometheus job; port 8889 remains exported application metrics. Include queue capacity/occupancy, failed/refused/dropped telemetry, exporter throughput, and Collector resource usage. Verify actual metric names in 0.160.0 before writing alerts. See [Collector internal telemetry](https://opentelemetry.io/docs/collector/internal-telemetry/).

Acceptance: during a five-minute backend outage API requests remain healthy with bounded memory; after recovery queues drain and all records known to have reached the persistent queue are queryable, allowing duplicates. Restart with that queue populated preserves those records. Forced restart, expired retries, queue overflow, and full-volume tests report measured losses and visible failure metrics. Prometheus exposes Collector health independently of its application-metric exporter.

## Phase 6 — Retention, cardinality, useful dashboards, and alerts

Files: Prometheus/Loki/Tempo configuration; both Compose files; Grafana datasources/dashboard JSON; new Grafana alert provisioning files; configuration test fixtures; operations docs.

1. Set explicit starter retention: Prometheus 15 days plus a documented size ceiling (initially 5 GiB on a suitably provisioned disk), Loki 7 days with the required compactor retention/deletion settings, and Tempo 24 hours. Keep at least 20% free disk headroom in the deployment budget and explain that a time limit is not a hard filesystem quota. Configure bounded container stdout rotation too. Verify against [Prometheus storage](https://prometheus.io/docs/prometheus/latest/storage/), [Loki retention](https://grafana.com/docs/loki/latest/operations/storage/retention/), and [Tempo configuration](https://grafana.com/docs/tempo/latest/configuration/); do not assume a retention field alone activates Loki deletion.
2. Disable blanket resource-to-label conversion. Promote only the explicitly required bounded resource labels for service/environment selection; preserve per-process series identity via the exporter-supported `job`/`instance` mapping and `target_info` as verified in integration tests. Never remove instance identity in a way that conflates concurrent counter producers. Keep build/version and instance metadata available for diagnosis without copying every resource attribute onto every metric.
3. Explicitly configure Loki's indexed resource attributes; keep instance/message/trace IDs as structured metadata, not index labels. Grafana documents this tradeoff in [Loki OTLP ingestion](https://grafana.com/docs/loki/latest/send-data/otel/). Prohibit raw paths, request IDs, actor/organization IDs, email, SQL text, and freeform exception messages as metric dimensions. Set source-side cardinality limits/attribute caps and monitor overflow/series growth.
4. Add service/environment selectors to all dashboard expressions, preserve outbox `outcome`, and verify the emitted HTTP/database histogram names. Add a Collector health panel for backlog, export failures, drops and scrape availability. Exercise trace-to-log navigation using trace IDs; remove the service-map configuration unless a tested metric source actually supports it. Do not add a metrics generator solely to justify a placeholder panel.
5. Provision a small alert set through the existing Grafana alerting capability, avoiding a new Alertmanager container: Collector unavailable, sustained queue occupancy above 80%, telemetry rejection/drop, backend scrape failure, service error-rate/latency threshold, and outbox failures. Add series-growth and storage/headroom panels/alerts only against signals actually exported. If the current stack lacks host-volume capacity metrics, document the host monitoring requirement explicitly instead of shipping nonfunctional disk alerts.
6. Give each rule a service/environment scope, minimum traffic condition where applicable, hold period, no-data/error behavior, severity, and runbook link. Treat initial application thresholds (for example 5% 5xx with sufficient traffic for five minutes) as tunable operational warnings, not contractual SLOs. Provision rules without embedding destinations; a staging operator configures one notification contact point and proves delivery before production qualification.

Acceptance: dashboard panels return data for two services/environments without mixing them; new identity attributes do not multiply labels unexpectedly; 1,000 distinct request paths/organization contexts do not create 1,000 series or Loki streams. Retention configuration validates and a shortened-retention isolated fixture demonstrates eventual deletion where feasible. Alert fixtures cover normal, firing, no-data, and recovery behavior, and staging confirms delivery to the configured contact point.

## Phase 7 — Automated verification and template regression coverage

Files: new root `scripts/test-observability.sh`; `scripts/test-template.sh`; root `.github/workflows/ci.yml`; generated `.github/workflows` backend workflow (use its actual existing filename); integration-test fixtures/projects; `Directory.Packages.props` and lockfiles only when necessary.

Build verification alongside each phase; this phase assembles the gates:

| Gate | Required evidence |
| --- | --- |
| Fast contract tests | Resource equality/precedence, protocol path mapping, invalid settings, parent sampling, endpoint-free startup, bounded safe log formatting, health suppression. Use a recording receiver and real registered providers; avoid tests that mirror private implementation helpers. |
| Pinned configuration validation | Both Compose variants and the TLS overlay render using synthetic environment values. Run the Collector's own validation command, Prometheus `promtool` configuration validation, Loki's supported config verification, and a bounded Tempo startup check when a validation-only command is unavailable. Provision Grafana in a container to verify dashboards, datasources and alert definitions. YAML parsing alone is insufficient. |
| Three-signal end-to-end smoke | Generate one normal request, one sanitized failure, and an outbox event; query Loki, Tempo, Prometheus, and Grafana with bounded polling. Assert correlation and resource identity, not just HTTP 200 from backend health endpoints. Use a known sampled trace in this test so sampling cannot cause flakiness. |
| Privacy matrix | Exercise both real application input paths and direct OTLP malformed/adversarial fixtures; inspect stdout and all persistent/query surfaces with positive controls. Include restarts to ensure queued data is sanitized before persistence. |
| Recovery/transport matrix | Backend outage, unavailable Collector at API startup, graceful API stop, forced Collector restart, TLS/auth failure, bounded overflow/disk failure, and observable recovery. Keep expensive destructive fixtures on isolated named volumes owned by the test harness. |
| Template generation | Generate React and `--ui none` applications, including a dotted/hyphenated name, and validate resource names, configuration mounts, new files, and workflows. | AppHost | Start AppHost with a bounded test harness and verify all backend routes and signal delivery; ensure HTTP/protobuf and container DNS work under Aspire rather than inferring success from Compose. |

Run fast tests, pinned config checks, and a short three-signal smoke on pull requests; run five-minute outages, destructive-volume fixtures, retention aging, and representative-load qualification in a dedicated scheduled/manual CI job or staging workflow. Place tests before the existing CI disk-pruning step, set explicit timeouts, and upload sanitized diagnostic artifacts on failure. Never copy production configuration/secrets into test fixtures. Avoid global environment-variable races by using isolated test-host configuration or subprocess isolation.

Acceptance: CI detects a wrong OTLP protocol, missing allowlist, bad Collector key, broken histogram query, public telemetry port, duplicated logs, and lost queued telemetry. All existing solution/template checks remain green. Generated applications receive runnable verification instructions without dependencies on the template repository's private paths.

## Phase 8 — Operational handoff and Aspire deployment role

Files: `templates/trykatch/docs/operations.md`, `docs/threat-model.md`, template README variants; `docs-site/src/content/docs/operations/observability.md` and French counterpart; root and template `docs/adr/0004-otel-grafana-stack.md`; AppHost run/publish guards if needed.

1. Document supported development/staging/production configuration, identity precedence, sampling tradeoffs, safe instrumentation rules, ingress restrictions, recovery/loss budgets, retention, alert setup, backup ownership, and how to inspect/rotate a Collector volume. Include rollback steps and measured qualification results with hardware/workload/version context.
2. State the Aspire distinction precisely: AppHost run mode/DCP orchestrates local development and tests; ServiceDefaults is deployed with the application; AppHost publish mode can generate deployment artifacts; a target platform runs production workloads. [Aspire architecture](https://aspire.dev/architecture/overview/) and [deployment documentation](https://aspire.dev/deployment/deploy-with-aspire/) describe these separate roles.
3. Keep checked-in Compose as this template's deployment authority for this hardening effort. The current AppHost does not configure a production publisher; do not claim `aspire publish` already yields equivalent production artifacts. Document publish as an available future CI input, and `aspire deploy` as a target-specific deployment action requiring staging qualification. Do not add a speculative publisher migration to this plan.
4. Gate local demo credentials/resources to run/development mode so future publish use cannot accidentally carry them into deployment output. Describe the verification required before adopting a publisher: compare networks, resources, secret references, volumes, identity, migration ordering, and TLS policy against the maintained Compose contract; review the generated artifact in CI.
5. Keep Aspire Dashboard local and ephemeral. If operators later choose to host it for diagnostics, link to [official Dashboard security guidance](https://aspire.dev/dashboard/security-considerations/) and require a separate deployment design; the durable backends remain the operational record.

Acceptance: English/French operations docs and generated READMEs agree with the tested behavior; ADR language distinguishes run mode from publishing; a fresh generated application can follow the documented Compose setup; staging records successful signal, privacy, restart, capacity, and notification drills. Production qualification is only claimed for the measured topology and workload.

## Implementation order and release gate

Implement phases 1 → 2 → 3 → 4 → 5 → 6, adding each phase's tests immediately. Complete the combined phase-7 CI coverage and phase-8 operational handoff before the production qualification claim. Privacy enforcement must precede durable queue rollout so sensitive records are not persisted in the Collector. Resource/metric label policy must precede dashboard/alert finalization. Keep changes reviewable as focused commits without upgrading unrelated packages.

Release requires: all three signals and correlation proven; matching resources and protocol; no planted secrets on any tested telemetry surface; protected operational access; functional sampling/probe suppression; bounded outage behavior and documented loss windows; validated retention and alert delivery; healthy generated React/backend-only applications and AppHost; and recorded staging measurements. Unmeasured throughput/host-loss guarantees, external ingress/secret-store operations, and capacity beyond the qualification workload remain explicitly deployment-owned.
