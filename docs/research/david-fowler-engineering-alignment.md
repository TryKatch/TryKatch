# David Fowler engineering alignment

Reviewed 2026-09-11 against public primary sources and the current Trykatch source. This compares published guidance and sample implementation choices; it does not imply Fowler's or Microsoft's review or endorsement. PR numbers refer to the proposed enterprise-hardening sequence.

## Evidence and interpretation

**Explicit async guidance.** Fowler recommends async throughout the call chain, avoiding blocking task waits and `async void` in ASP.NET Core, propagating cancellation, and disposing timeout token sources. [AsyncGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/bcc7ca394eeb7113da6b3071f738ee5361b67db3/AsyncGuidance.md). Trykatch's [OutboxProcessor](../../templates/trykatch/src/Common/Trykatch.Infrastructure/Persistence/OutboxProcessor.cs) already awaits an asynchronous timer, creates an async scope per batch, and passes cancellation into database and delivery calls. [OutboxDelivery](../../templates/trykatch/src/Common/Trykatch.Infrastructure/Persistence/OutboxDelivery.cs) rethrows requested cancellation. A targeted scan of `templates/trykatch/src` found no `async void`, `.Result`, `.Wait(`, or `Task.Run` occurrences; this is a useful baseline, not proof of complete async correctness.

**Explicit request-lifetime guidance.** Do not retain or concurrently access `HttpContext`, or capture request-scoped services for background work; create a separate scope for that work. The first response write sends headers, so later middleware cannot freely replace the response. [AspNetCoreGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/bcc7ca394eeb7113da6b3071f738ee5361b67db3/AspNetCoreGuidance.md). Trykatch's worker scope aligns. Our inference: committing after `await next(context)` in [OrganizationTransactionMiddleware](../../templates/trykatch/src/API/Trykatch.Api/Security/OrganizationTransactionMiddleware.cs) and [PlatformDataTransactionMiddleware](../../templates/trykatch/src/API/Trykatch.Api/Security/PlatformDataTransactionMiddleware.cs) can report success before commit succeeds. A header callback alone does not solve this durability boundary.

**Sample endpoint pattern, not a universal architecture prescription.** TodoApp groups feature routes, applies authorization/rate limits/validation at the group, injects dependencies explicitly into handlers, projects read results, and uses typed results with ownership-aware update/delete predicates. Its list is unpaged and its handlers omit cancellation tokens; copying the sample wholesale would fall short of our enterprise requirements. [TodoApi.cs](https://github.com/davidfowl/TodoApp/blob/307a1eadbbd77a3004c318f2377e4818bc400af6/Todo.Api/Todos/TodoApi.cs). Trykatch's [ProjectsModule](../../templates/trykatch/src/Modules/Projects/Trykatch.Modules.Projects.Infrastructure/ProjectsModule.cs) already owns registration and permission declarations, while [module contracts](../../templates/trykatch/src/Common/Trykatch.Modules.Abstractions/TrykatchModule.cs) expose explicit host seams. Preserve those boundaries; the sample does not justify removing them or mandating Minimal APIs everywhere.

**Sample composition and syntax.** TodoApp's [Program.cs](https://github.com/davidfowl/TodoApp/blob/307a1eadbbd77a3004c318f2377e4818bc400af6/Todo.Api/Program.cs) uses framework DI and focused registration/mapping extensions; [TodoDbContext.cs](https://github.com/davidfowl/TodoApp/blob/307a1eadbbd77a3004c318f2377e4818bc400af6/Todo.Api/TodoDbContext.cs) uses a primary constructor. These support using concise modern C# when appropriate, not declaring primary constructors a universal Fowler standard. Trykatch already uses them in middleware and outbox services. Its [DI registration](../../templates/trykatch/src/Common/Trykatch.Infrastructure/DependencyInjection.cs) shares scoped implementations across interfaces. The [migrator](../../templates/trykatch/src/API/Trykatch.Migrator/Program.cs) builds and asynchronously disposes a dedicated module provider with scope validation; that isolated composition root is not automatically a duplicate-container defect.

## Concrete plan amendments

These are our engineering recommendations, informed by the evidence above and local code inspection.

| PR | Acceptance criteria to make explicit |
| --- | --- |
| 06 — transactions | Commit before reporting mutation success; inject commit failure and client disconnect. Define atomicity when application and control-plane contexts both write. Never retry the entire downstream HTTP pipeline. Preserve transaction-local tenant settings. |
| 07 — outbox | Keep hosted execution, async scopes, and cancellation. Test database outage, shutdown during publication, and publication followed by failed commit. Define bounded retry/backoff, terminal failure and replay, transport timeout, and consumer deduplication using the stable message ID. Current code holds row locks while publishing; measure this and choose a claim/lease design if required. Execution-strategy retries are not currently enabled in its Npgsql registration, but enabling them would require reviewing external side-effect replay. |
| 04 / 09 — leaks and telemetry | Classify and redact persisted outbox errors: `LastError` currently stores `exception.Message` up to 2,000 characters. Test that secrets cannot enter storage or exported telemetry through transport errors. Preserve structured, low-cardinality outcome metrics and safe exception-type logging. |
| 08 / 15 — concurrency and performance | Require bounded pagination, request cancellation, timeouts, upload/response size budgets, and shutdown tests. Test slow consumers and large payloads; async APIs alone do not establish bounded resource use. |
| 11 / 14 — contracts and maintainability | Add focused async/lifetime review checks and container validation where the complete dependency graph exists. Prefer explicit dependency seams and framework primitives. Record primary constructors as the team's optional/default style with justified exceptions; avoid a cosmetic rewrite release gate. Retain typed response contracts and test authorization consistently across endpoint styles. |

PRs 01–05, 10, 12–13, and 16 retain their existing security, reproducibility, tenancy, frontend, and release gates. These sources do not establish enterprise MFA, RLS, recovery, or release-certification requirements; those need their own primary standards and operational evidence. No product code was changed and no runtime qualification was performed for this research.
