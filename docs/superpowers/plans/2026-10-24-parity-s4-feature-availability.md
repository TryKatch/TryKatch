# Installed Feature Availability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans or superpowers:subagent-driven-development task-by-task. Preserve Sol/Luna ownership, root-owned .NET execution and one final integrated review.

**Goal:** Let operators control declared installed features per deployment environment and organization, with current server enforcement and matching browser availability.
**Architecture:** Explicit module declarations feed a neutral evaluator backed by the host control plane. Platform control writes and their immutable history share one transaction; organization requests read only safe policy and their own overrides. Availability never supplies permissions, entitlements, membership or module installation.
**Tech Stack:** Existing .NET 10/PostgreSQL/React/TanStack stack, current SDK 10.0.402 and EF/Npgsql 10.0.11, pnpm 10.17.1. No new dependency or infrastructure adapter.
**Spec:** Parent `docs/superpowers/plans/2026-10-23-parity-02-platform-services.md`, S4; `templates/trykatch/docs/specs/feature-parity-contracts.md`, section 8; acceptance permission matrix. Tasks 0–1 declarations, precedence and control persistence are implemented and locally verified. Request evaluation, administration APIs, enforcement and UI remain outstanding.

## Global constraints and lead rulings

- Keep explicit generated registries, module boundaries, same-origin cookies/CSRF, forced RLS and all five runtime profiles. Root owns architecture, security, migrations, .NET and integration. Bounded Luna assignments may edit only assigned files, never run .NET or spawn agents. One whole-branch independent review at the final gate, supplemented by the existing ECC checklist.
- Follow the already approved roadmap and continuous implementation/merge instruction. This plan settles technical mechanisms within S4; it does not reopen D2/D3/D4 or add business scope. Keep RustFS. S5/S6 and every later roadmap/release gate remain required.
- Add optional `features` metadata to the existing closed manifest v1 through the same additive evolution used for execution/realtime metadata; absent metadata means an empty declaration set. Each declaration has a required key, name, description and explicit Boolean default. Bound declarations to100per module, nonblank names to160characters and nonblank descriptions to1000characters. No new module capability or assembly scan.
- Descriptor/manifest parity has no existing feature seam. Generate explicit manifest expectations into API/migrator registries and validate them against the already explicitly instantiated modules; add neutral `InstalledModuleFeature(ModuleId, Feature)` and `ModuleFeatureRegistrationRules.ValidateManifest(modules, expected)` called by a generated static constructor. No source parsing or assembly scan. The Web catalog gains an optional third expected-feature argument for source compatibility; generated registries always provide it, including an empty array for legacy modules. Match keys, names, descriptions and explicit defaults, independent of declaration order. Root owns the neutral guard; CLI generation and SDK enforcement use this same shape.
- Feature keys use the existing stable contract-key syntax, maximum 120 characters, and their owning module prefix. `projects.reads` and `projects.writes` default true to preserve existing behavior; they are distinct from `projects.read` / `projects.manage` permission keys. Unknown/absent/disabled module features are false, even if stale controls/configuration request true. Stable keys cannot be repurposed for unrelated behavior.
- Precedence: installed declared feature -> deployment hard-disable veto -> platform force-disable veto -> nullable organization override -> nullable environment default -> configured default -> declared explicit default. Any veto wins. Environment identity is server-derived from `IHostEnvironment.EnvironmentName`, normalized invariantly, bounded to 64 safe ASCII characters; APIs cannot select an environment.
- Configuration uses `Features:Disabled` and `Features:Defaults`. Validate key/value/environment shape at startup. Retained well-formed configuration for absent modules never loads or authorizes those modules.
- Read policy and organization override in one PostgreSQL statement. No feature availability cache, stale-enabled fallback or dependency on distributed-cache availability. Database failure becomes a distinct unavailable error; cancellation retains cancellation semantics. Gate protected cached DTOs before returning them.
- SQL control identities are `(environment, featureKey)` and `(environment, organizationId, featureKey)`. Reset an override to NULL with a new Guid version; retain the row to prevent ABA and preserve disabled-module settings. Each admitted save requires exact expected version (`Guid.Empty` only for a missing row), changes version and appends bounded before/after history atomically.
- Use a transaction advisory **try-lock** on the full control target. Contention returns a bounded busy result; no lock wait or automatic save retry. Check strict current platform authority before disclosure and again after acquisition. Admission is the second check: later revocation does not retroactively cancel an already admitted transaction. Do not claim cross-database serialization/atomicity with Identity. This simplifies the earlier consultation's optional waiting-lock design.
- Use `IPlatformAuthorityReader.ReadAsync(actorId).HasPermission(...)`, not legacy administrator fallback. Match the supplied actor with `app.actor_id` in the active platform-profile transaction; no missing-transaction or impersonated organization fallback. New platform permissions initially belong only to the actual Administrator; Operator/Auditor/custom roles get no automatic grant expansion.
- New exact host relations: `platform.feature_environment_controls`, `platform.organization_feature_overrides`, `platform.feature_control_history`. Platform runtime can SELECT/INSERT/UPDATE controls and SELECT/INSERT history; organization runtime can SELECT safe environment controls and its own overrides only. Identity/outbox/coordinator profiles receive no access. No runtime DELETE; history has no UPDATE. FORCE RLS; actor-bound insert/update checks and current-org read predicates. Updating a row must not require being its previous editor.
- Map these control-plane records in `PlatformDbContext` and its inherited organization context. Control-plane-only reserved resource descriptors omit `EntityType`, following existing host allocation records. Any exception permitting an organization-owned reserved platform relation is exact and host-only; a module cannot spoof it or broaden its own SQL ownership.
- History is a dedicated immutable platform control ledger in the same control transaction, since the existing organization `AuditIntentWriter` requires organization membership/business context. Do not fabricate a membership to reuse it. Fixed typed before/after fields, actor, target, versions and timestamp; no arbitrary JSON, secrets or client actor/environment fields. Editor identity lives only in platform-private history; control rows contain safe policy values/version/time. Control write RLS requires a nonempty actor, history insert binds its actor to `app.actor_id`, and the host store verifies its caller matches that ambient actor.
- Control-plane mappings belong only to `PlatformDbContext` and its inherited organization context, never `ApplicationDbContext`. The override is not a business `IOrganizationOwned` entity and has no application EF filter; current organization selection and forced PostgreSQL read policies enforce its scope while the platform role can administer different organizations. Its reserved host-only access exception is exact. Environment identifiers use normalized lowercase ASCII alphanumeric/dot/underscore/hyphen characters, start alphanumeric and remain at most 64 characters. Stored feature keys must be stable and contain an owner separator. History uses nullable typed previous version/value/force fields, a fresh nonempty version and target organization; force fields apply only to environment targets. Organization/history foreign keys restrict deletion.
- Disabled availability returns `feature_unavailable` (HTTP409), permission denial remains403, and policy infrastructure failure returns503 `feature_policy_unavailable`. An absent module retains its ordinary missing routes. No new state-changing assistant tool.

## Review focus

1. A true feature cannot add permissions, revive an absent module or bypass a deployment/force-off veto (Tasks0/2/3).
2. Rendered controls and old successful idempotency receipts cannot bypass a newly disabled write policy; direct/queued/assistant callers use the same application boundary (Task3).
3. A revoked/suspended/legacy-only platform actor cannot change controls/history, and the organization profile cannot inspect another organization's controls or operator history (Tasks1/2).
4. An infrastructure outage or late response from a previous workspace cannot leave a stale enabled browser decision or return a protected cached DTO (Tasks2/3/4).
5. Disabling/re-enabling a module preserves control/history rows and committed business data; read and write kills stay independent (Tasks2/3/5).
