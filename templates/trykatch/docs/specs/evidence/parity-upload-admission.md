# Upload admission and Documents integration evidence

This checkpoint qualifies the S5 host upload lifecycle and its production Documents use case/API integration against actual PostgreSQL runtime roles and the real local conditional object adapter. Documents now declares `documents.upload` and uses durable admission and conditional writes. Earlier host component tests used a test-only declaration; the composed HTTP cases use the production module descriptor, request middleware, use case, audit/outbox persistence and storage adapter. Closed removal accounting and leased maintenance execution remain required.

## Implemented boundaries

- `ModuleUploadAdmission` requires the existing shared ReadCommitted parent transaction and current original user membership/compiled upload-policy permission. A fresh child scope begins/enlists its own transaction, resolves access again and publishes before acquiring the common resource lock. Upload-kind hold, immutable upload operation and closed recovery reference commit together before a private receipt is returned.
- Receipts bind issuer, actual provider transaction and EF owner transaction lifetime, policy, original actor/membership, payload and metadata identity, stable subject/key and actual storage namespace. Changed identities conflict. Expired admission cannot be renewed or finalized. Existing committed retries skip the metadata callback.
- Finalization verifies the current owned provisional object and runs metadata, audit, outbox, exact positive ledger effect and both completion transitions within the parent transaction. Callback/accounting failure leaves its commit guard incomplete, even when the caller handles the original failure. Sequential pre-admitted uploads share the parent's atomic outcome.
- `ModuleUploadFencing` uses fixed empty-permission technical scopes. It commits Fencing under the same nonblocking resource lock, disposes that transaction, conditionally confirms a permanent sentinel, then revalidates and releases the hold in a fresh transaction. Busy finalization, committed state, mismatched identity/namespace and unconfirmed storage never permit release. Current user membership is not required to compensate the original host-issued admission.
- Incomplete declared inventory queues one active inventory reference, including when finite upload admission is unavailable. The actual organization role performs this with INSERT only and no queue read privilege.
- Documents computes its canonical fingerprint, supplies a legacy server UUID only when omitted, registers rollback fencing before PUT, and finalizes through the host callback. Neither previous raw-delete compensation path remains. Completed retries revalidate admission and load the current authorized Active/Archived DTO without repeating metadata/audit/events; pending-deletion and missing results cannot be recreated.
- The first-party dialog retains its operation UUID for the same selected File and normalized metadata. Meaningful edits, a new file/dialog session or another organization allocate another logical operation. Multipart rejects empty, malformed, duplicate and all-zero operation UUID fields before hashing or admission. Organization and actor remain request-derived.

## Failures investigated

The initial service scaffold returned Unavailable: both initial reservation cases failed. Once reservation was implemented,9 reservation cases passed while4 finalization cases failed against the unavailable finalization scaffold. Implementing finalization made those4 pass. All4 cancellation cases failed against the cancellation scaffold and passed after the fixed fencing lifecycle was implemented.

An existing final-slot test failed in a combined run and again in isolation: concurrent entitlement publication could return `quota_unavailable` before the test reached its intended resource-slot contest. The fixture now publishes both participants before starting that contest. It retains the original `quota_busy`/exhaustion assertions and does not weaken the admission contract. All48 selected existing quota/publication cases then pass. A Name-equality filter initially omitted three parameterized methods; their6 data cases were explicitly selected and qualified afterward.

Compiler errors during development included a static fixture-helper requirement, a missing host context-initializer namespace and duplicate primary-constructor parameter capture. They were corrected before behavioral qualification. No production exception handling was weakened to silence these errors.

Documents orchestration first failed compilation on the missing command/constructor contract, then failed nine of ten semantic cases while the legacy raw upload path was still active. The implemented flow passes those cases; additional denial and concurrent-completion cases also pass. The first HTTP run passed three cases and stopped two on test fixture errors: `/access` has no actor ID, and membership updates require a nonempty role list. The fixtures now read the actor from the authenticated session and revoke management by updating the assigned role. A further fixture assumption that existing document `sizeBytes` is serialized as a string was contradicted by actual HTTP output; the assertion preserves its existing bounded JSON number transport. OpenAPI permits integer/string for that legacy field. This does not change the later quota-usage endpoint's explicit Int64-string requirement.

Module generation and doctor succeed; API build regenerates the optional UUID and error-response OpenAPI contract with zero warnings/errors. Normal client generation, affected API-client/Documents/host/Storybook typechecks and affected production builds pass. Production output excludes Storybook assets and fixture sentinels; assistant generation check passes. Actual current-worktree browser inspection covers the upload dialog at 320px and 768px in English/light and 1440px in French/dark; the phone dialog scrolls to reachable actions. These browser previews use sample data, while the separate HTTP tests qualify backend effects.

## Remaining acceptance

This does not yet prove a generated application's browser-to-backend upload journey, closed removal/refund policy, leased claims/worker restart, two API replicas with RustFS, packed/renamed generated outputs, request throttling, usage UI, whole-S5 review/CI/merge or the final main-branch release. Those gates remain required by the canonical S5 plan and overall parity roadmap. S3/RustFS adapter evidence from Task4 remains separate; this checkpoint makes no physical purge or power-loss durability claim.
