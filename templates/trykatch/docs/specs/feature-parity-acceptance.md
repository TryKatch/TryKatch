# Feature parity acceptance and permission matrix

**Status:** Phase 0 contract baseline with E1–E4 implementation evidence linked below. Later parity behavior remains planned or explicitly deferred. E4 still awaits PR merge gates; this matrix does not establish release readiness.
**Source baseline:** `origin/develop` at `d3e8dc40b6c5d4d20a173ec2f884353f4f25a7d9`, inspected 2026-10-23.
**Contract ledger:** [Feature parity contracts](feature-parity-contracts.md) (created in P0.1).

Maintainer source (repository root, not shipped with generated applications): `docs/superpowers/specs/2026-10-23-feature-parity-design.md`.

This matrix makes the proposed parity scope falsifiable. `planned` means a future acceptance case and test owner are identified; `implemented` means the behavior exists in source; `verified` means the named check ran and passed with evidence recorded; `deferred` means a stated policy or deployment gate prevents claiming the behavior. A source-inspected baseline is labeled separately and never upgrades a future feature to implemented. The status column distinguishes verified execution/job behavior from remaining planned module behavior and explicit `deferred` gates. Existing Projects/Documents grant behavior described as baseline remains **source-inspected only**. Phase 0 itself ran no runtime tests; later evidence is linked per acceptance row.

## Module combinations and selection contract

`trykatch.modules.json` remains authoritative. Module bundles may be present in source while disabled. The existing module enable/generate workflow selects modules and resolves declared dependencies atomically; do not add a new `--modules` CLI switch or overload existing flags. The resulting installed catalog, generated API/Web registries and lockfile must agree. Validate declared capability and adapter configuration statically without live credentials, external network probes or secret disclosure during template generation/build. Runtime readiness and deployment qualification are separate evidence.

| Selection | Required | Optional | Acceptance when optional item is absent |
| --- | --- | --- | --- |
| Notifications | None | Email adapter; publishers from installed modules | Inbox/read-state works without Chat, Billing or email. Only installed publishers contribute events; absence of email means inbox-only delivery. |
| Webhooks | None | Event publishers from installed modules | Subscription and delivery work only for explicitly exported events; no historical event backfill. |
| Billing | None | Notifications and email adapter | Billing domain does not require either. Invoice inbox/email integrations are omitted when absent. |
| Catalog | Documents business module and registered storage capability (each independently required) | Notifications | Image capability uses Documents-backed opaque attachments; missing either requirement rejects Catalog selection. |
| Tickets | None | Notifications | Ticket workflow remains usable; without Notifications no inbox event is promised. |
| Chat | Documents business module and registered storage capability (each independently required) | Notifications | Messaging/attachments work without Notifications; mention-to-inbox integration is conditional on Notifications being installed. Missing either requirement rejects Chat selection. |
| Documents | No other business module | Storage adapter | Existing standalone Documents remains; owner-bound attachment reads deny if the owner's policy/module is missing. `--documents` still means optional spreadsheet/PDF exporters. |
| Host quotas/entitlements | None | Billing publisher | Host configuration is usable without Billing. Quotas default Disabled; Enforced resources need a finite limit or explicit unlimited setting. Billing publishes a projection and is not a kernel dependency. |

The full parity profile is Documents with storage plus all six new modules. It is a convenience profile over the same catalog and explicit dependency validation, not an implicit default install. Disabling/unregistering a module turns off its behavior and retains its data/history. Feature flags and billing plan state cannot install code or grant permissions.

## Organization permissions and initial defaults

Permission names below are proposed stable IDs for the implementation specs and contract ledger. They are scoped to the active organization except where explicitly called platform permissions. Organization authorization, resource ownership checks and database RLS remain separate layers; a permission alone never substitutes for row ownership or recipient/channel checks.

| Permission ID | Intended operation | Initial default grant | Required guard |
| --- | --- | --- | --- |
| `notifications.read` | Read own inbox and unread count | Owner, Admin, Member, Viewer | Recipient is always the current principal; cannot read another member's inbox. |
| `notifications.manage` | Mark one own notification read or mark all own notifications read | Owner, Admin, Member, Viewer at organization creation under the default grant catalog | Same self-only recipient rule; there is no dismissed operation or preference/subscription administration in this scope. Existing non-Owner grants are not automatically broadened. |
| `webhooks.read` | Read own organization's subscriptions, exports and delivery status | Owner only | Subscription and delivery rows are organization-scoped; secrets are never returned. |
| `webhooks.manage` | Create/update/disable subscriptions and secret rotation | Owner only | SSRF, destination validation, encrypted secret and explicit exported-event checks apply. |
| `webhooks.test` | Request one bounded test delivery | Owner only | Reuses destination controls and rate limits; does not expose unrestricted network access. |
| `webhooks.redeliver` | Request controlled delivery retry | Owner only | Existing delivery scope, attempt limits and audit apply; no arbitrary payload target. |
| `billing.read` | Read plan projection, subscription and invoices | Owner only | Billing visibility is organization-scoped; no platform plan-write capability. |
| `billing.manage` | Manage organization subscription terms/lifecycle | Owner only | Commercial policies blocked by D2 remain unavailable. |
| `billing.settle` | Mark an invoice paid/settled through the supported manual workflow | Owner only | Does not imply payment collection, gateway access or arbitrary amount changes. |
| `catalog.read` | Search/list/read products, categories, brands and stock | Owner only | Resource and attachment owner policies still apply. |
| `catalog.manage` | Manage catalog entities, images and lifecycle | Owner only | Category-cycle, SKU uniqueness, exact-money and concurrency rules apply. |
| `catalog.stock` | Apply stock adjustments | Owner only | Adjustment is auditable and concurrency-safe; cannot edit issued billing history. |
| `tickets.read` | Read tickets visible in the organization | Owner only | Resource visibility remains explicit; no cross-organization access. |
| `tickets.create` | Open tickets in the current organization | Owner only | Reporter derives from authenticated actor where caller identity is relevant. |
| `tickets.manage` | Change ticket fields/state and comment under allowed transitions | Owner only | Current state, concurrency and transition legality are revalidated. |
| `tickets.assign` | Assign/reassign a ticket | Owner only | Target assignee must be eligible in the same organization. |
| `chat.read` | Read channels/messages visible to the actor | Owner only | Current channel membership and message-level visibility are checked in every query/search. |
| `chat.write` | Send/edit permitted messages and reactions | Owner only | Current membership and resource policy are checked at mutation time. |
| `chat.manage` | Manage channel membership/settings and pins/archive | Owner only | Cannot grant above actor's authority; channel ownership rules apply. |
| `chat.moderate` | Perform explicitly defined moderation actions | Owner only | Exact actions and audit requirements must be enumerated by Chat spec before implementation. |
| `groups.read` | Read organization user groups | Owner only | User groups are organization-owned; no global Identity role substitution. |
| `groups.manage` | Manage organization user groups within the actor's delegation ceiling | Owner only | Cannot delegate permissions the actor does not hold; preserve last-Owner safeguards. These are user groups, not permission-catalog grouping. |
| `organizations.manage` | Change organization brand settings | Existing organization-management grant policy; do not add a broader non-Owner grant here | Validated assets/settings and current organization context; branding stays separate from product-wide defaults. |

Existing `projects.*` and standalone `documents.*` permission IDs/defaults remain unchanged. Listed defaults are the creation-time/default grant catalog only. Existing Owner grants are persisted snapshots seeded at organization creation, not dynamically expanded when the catalog changes. New module permissions therefore require S6's audited, idempotent Owner/catalog reconciliation for already-existing organizations. Reconciliation must preserve configured non-Owner grants; installation must not silently broaden them. Notification self-service defaults do not authorize broadening existing non-Owner grants. No other automatic new non-Owner grants are proposed. In particular, session self-service policy must be defined by its owning identity spec and derives the user from the current principal; it is not a target-user administration grant.

## Platform permissions and actors

Platform permission IDs use a separate catalog and never create organization membership or bypass organization RLS.

| Permission ID | Platform operation | Initial default |
| --- | --- | --- |
| `platform.work.read` / `platform.work.manage` | Inspect and control bounded host work operations | Platform Administrator only |
| `platform.features.read` / `platform.features.manage` | Inspect/change platform feature controls | Platform Administrator only |
| `platform.entitlements.read` / `platform.entitlements.manage` | Inspect/change host entitlement configuration/projections | Platform Administrator only |
| `platform.billing-plans.read` / `platform.billing-plans.manage` | Read/edit platform-owned billing plans | Platform Administrator only |
| `platform.support.delegate` | Issue explicitly bounded, audited support delegation | Platform Administrator only, and only when D4 is approved and required assurance is present |
| Existing `platform.users.manage` | Privileged platform user/session administration | Existing catalog/defaults only; retain its current meaning |

Platform Administrator receives published catalog grants through the existing role model. Platform Operator, Platform Auditor and custom roles receive no automatic new grants. Their persisted grants remain unchanged until an explicitly audited grant operation. Organization self-session operations never accept an arbitrary target user; privileged session administration uses the existing `platform.users.manage` permission and a separately authorized platform surface.

## Source-inspected baseline and verification record

The current source confirms an explicit module catalog and separate module enable/generate lifecycle ([catalog](../../trykatch.modules.json), [module guide](../modules.md)); it does not establish the new module IDs, dependencies or permissions proposed here. The current module tool has its existing module generation and enablement paths ([ModuleScaffolder](../../tools/Trykatch.ModuleTool/ModuleScaffolder.cs)); no new CLI flag is proposed. Existing `--documents` exporter selection and `--storage` adapter configuration are separate concerns. Current Projects and Documents permission identifiers and defaults are reviewed as baseline only; future parity grants must not alter them. [`Role.AddMissingPermissions`](../../src/Common/Trykatch.Domain/Organizations/Role.cs) exists, and [DevelopmentDemoSeeder](../../src/API/Trykatch.Api/Development/DevelopmentDemoSeeder.cs) uses it to repair development demo roles. That is not a production-wide S6 upgrade or evidence that existing organizations receive new grants. S6 remains required for production organizations.

Organization authorization and platform authorization remain distinct. Current organization transaction boundaries establish organization/actor context before data access, while runtime database profiles distinguish organization and platform relations ([runtime profiles](../../src/Common/Trykatch.Infrastructure/Organizations/RuntimeDatabaseAccessProfiles.cs), [isolation guide](../module-data-isolation.md)). This is source inspection, not evidence that proposed new permissions, RLS policies, async grants, adapters or module routes exist.

Phase 0 runtime acceptance status at its checkpoint was **planned, not implementation**. Documentation link/structure checks and packed renamed React/backend-only payload generation are recorded in [Phase 0 evidence](evidence/feature-parity-phase-zero.md). No generated application build, runtime, PostgreSQL, browser or deployment check was run during Phase 0. Subsequent E1–E4 evidence records focused runtime checks, including renamed React/backend-only E4 outputs, real PostgreSQL and mocked-API browser flows. This does not qualify the future full module matrix (A18) or multi-process failover (A17). Remaining planned test names above must be replaced or linked to actual cases by implementation owners and marked `implemented` or `verified` only with recorded results. The release evidence must retain `deferred` status for unresolved gates even if independent module tests pass.
